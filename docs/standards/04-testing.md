# 04 测试规范

| 项目 | 内容 |
| --- | --- |
| 规范编号 | `04-testing` |
| 掌管范围 | 测试来源、层次、组织、数据隔离、外部依赖、通过判定、断言有效性、响应时间、变更要求 |
| 落地方式 | 常驻约束写入 `.cursor/rules/campusclaw-standards.mdc`；“按规范补测试”写成技能 |
| 违反时 | 测试不绿不得勾选任务；不得保留“已知失败”或跳过无理由用例 |

## 这一页管什么

测试的输入是规约里的场景；用例清单应当是场景清单的镜像。规约变更后，用例必须同步修改。

不管：断言的具体写法、框架 API 归语言通行做法；越权用例的内容归 `03-security.md`。

## 项目事实

- 单元测试：`backend/internal/**/*_test.go`，`go test ./...`。
- 接口测试：`scripts/verify.py`，按 README 启动 Compose 后运行，结果写 `docs/verification.md`。
- 端到端：`frontend/e2e/`，Playwright，桌面 1440×900 和手机 390×844 各跑主路径。
- 本地模式：`EMBEDDING_URL=local`、`CHAT_URL=local` 时不访问真实网关；Qdrant 和 MySQL 由 Compose 提供。
- 测试数据：只用预置账号 `teacher_a`、`student_a1`、`student_b1` 和测试上传的临时材料；生产数据不进测试环境。
- 当前 change 的验收入口：`openspec validate --strict`、`python3 scripts/spec_check.py`、`python3 scripts/standards_check.py`、`go test ./...`、`python3 scripts/verify.py`、`npx playwright test`。

## 规范条目

| 条目 | 项目事实 | 为什么 | 怎么检查 |
| --- | --- | --- | --- |
| 测试层次 | 单元测覆盖业务规则（切片、偏移、迁移、状态机、409、分页）；`verify.py` 覆盖每条能力的正常/失败路径；Playwright 只覆盖 3 条主路径 | 端到端跑所有细节会慢且脆，单元测不覆盖接口会漏集成问题 | 统计三层用例；主路径外出现端到端用例即错位 |
| 用例来源 | 每个 Scenario 至少一组用例；用例名或注释写 `capability/requirement/scenario`，可双向追溯 | 没有来源的用例会随实现漂移 | 场景清单与用例文件逐一比对；无归属用例不合并 |
| 三类组织 | 正常、失败、边界分开；失败路径数不少于需求条数；边界取等价类两端（0/1、20/21、100/101） | 只测正常路径无法发现权限和限额问题 | 目录或命名能看出三类；缺一类即未完成 |
| 数据隔离 | 每条用例创建自己的材料/标签/进度，结束后清理；不依赖执行顺序和残留数据；随机顺序运行结果一致 | 依赖残留数据会让单独跑和全量跑结果不同 | 打乱顺序运行两次；清空测试数据后重跑 |
| 外部依赖 | Qdrant、嵌入、对话网关、时钟用可注入替身；断网后测试仍通过；Qdrant 停止场景单独跑 | 真实外部服务不可控，故障场景无法稳定复现 | 断网运行单元测；停 Qdrant 跑 `keyword`/`vector` 场景 |
| 一键运行 | README 写清命令、环境变量、退出码和报告位置：`go test ./...`、`python3 scripts/verify.py`、`npx playwright test` | 新成员按文档跑不起来，测试等于不存在 | 新成员按 README 从干净克隆执行一次 |
| 通过判定 | 失败以非零退出码阻断；不得保留“已知失败”；跳过必须写理由和登记人 | 绿色但带跳过会掩盖真实缺陷 | 检查退出码和跳过列表；跳过数只减不增 |
| 断言有效性 | 判据：改坏被测逻辑，用例是否变红；只断言状态码不断言数据变化是不够的 | 形状相同的错误无法被发现 | 对被测逻辑做一次等价破坏（如把 404 改成 403），用例应失败 |
| 缺陷判定口径 | 有业务 code 时只看 code；无 code 时按接口文档 HTTP 码；文档未写才用兜底表 | 把“HTTP 200 但业务拒绝”误判为成功很常见 | 构造 200 + `{error}` 响应，检查用例是否判失败 |
| 四个判定词 | “被当成成功”“被放行”“被误拒”“未处理故障”在评审表里定义；堆栈或无信息文案算未处理故障 | 评审人对“失败”的理解不一致会导致结论不可复现 | 随机抽 5 条失败用例，两人独立判定应一致 |
| 响应时间 | 正向用例：超过 50ms 标记，超过 100ms 不通过（项目值，可按环境调整并记录）；负向用例不计入 | 没有阈值就无法发现性能退化 | 每条正向用例记录耗时；超过阈值输出报告 |
| 变更要求 | 每次变更至少补对应场景用例；修缺陷先补能复现的用例 | 没有复现用例的修复很容易回归 | 变更说明与新增用例对照；缺陷单必须链接用例 |

## 本课最小集合

1. README 的一键命令、环境变量、退出码和报告位置。
2. 一条能力的三类用例（正常/失败/边界）：建议从“上传多格式材料”或“跨班 404”开始。
3. 数据隔离约定：独立数据、用例前后清理、随机顺序。
4. 健康检查用例：`/health` 200 且不查库；`/ready` 在依赖停止时 503。
5. 失败即阻断，约定当天失败用例由谁修。
6. 把“按规范补测试”写成技能或至少写成任务模板。

## 违反时怎么处理

- 用例没有对应 Scenario：补来源或删除用例。
- 只断言状态码、不断言数据变化：补断言。
- 测试依赖执行顺序或残留数据：改为自清理并随机顺序验证。
- 失败用例被标记为“已知失败”或跳过：阻断合并；修不了就拆小或回退。
- 例外（例如依赖真实课程网关的联调用例）：写进本规范，标注只在手动清单执行。
